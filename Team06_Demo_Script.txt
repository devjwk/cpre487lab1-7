[SLIDE 1] Team 06 – Jongwoo Kim – Lab 6
--------------------------------------------------------------------------------

Hi everyone, I'm Jongwoo from Team 6.

When I started Lab 6 on the lab machine, the first thing I looked at was why the naive code was taking 144.7 milliseconds.
When I checked the memory layout, I saw that the weights are stored in output-channel order, so having the input channel in the innermost loop made the CPU jump by 32 in memory on every single step.
So I thought, if I move the output channel (m) to the innermost loop, the CPU can just read the weights one by one in order, and keep the same input value in a register for all 32 channels.
As you can see in the top-left plot, doing that made the weight access completely sequential, and my latency dropped from 144.7 down to 27 milliseconds—about 5.4 times faster without changing the math at all.

Next, for tiling, I honestly expected small tiles to be faster because they fit easily in L1 cache.
But when I saw Tile 2 jump up to 235 milliseconds, I realized that the extra loop overhead and boundary checks were costing way more than the cache benefit.
As I increased the tile size, it got faster, and Tile 32 worked best at 27.4 milliseconds because it matched our 32 output channels.

For multithreading, I thought splitting the work across output rows with std::thread made the most sense so threads wouldn't fight over the same memory.
That gave me my best time of 8.21 milliseconds at 4 threads, which is a 17.6x speedup.
When I went from 8 up to 64 threads, it actually slowed down, and I realized that's because we create and join threads on every layer, so the thread overhead starts beating the parallel speedup.

Seeing how much memory access mattered on the CPU led right into how I approached Lab 7 on the next slide.

[SLIDE 3] Team 06 – Challenges & Takeaways
--------------------------------------------------------------------------------

Looking back at the challenges, both labs really showed me where the real bottlenecks are.
In Lab 6, seeing small tiles and high thread counts run slower showed me how easily software overhead can wipe out theoretical speedups.

In Lab 7, the two trickiest parts were getting the 5-loop address jumps right in index_gen, and getting the BRAM read-and-write timing right for MaxPooling in output_storage.
Specifically, when I looked at the last write cycle in the waveform, I noticed that if conv_complete turns on in the same cycle as the final BRAM write, the accelerator goes idle one cycle too early.
So I thought, if I delay conv_complete by just one clock cycle, that last pooled byte will finish writing cleanly—and once I did that, the whole testbench passed.

Putting Labs 5, 6, and 7 together, my biggest takeaway is that moving data matters way more than the math itself.
In Lab 5, sending packets one by one over the FIFO held back a fast MAC. In Lab 6, reading memory in order gave a 5.4x speedup. And in Lab 7, keeping activations in on-chip BRAM avoids slow DDR memory copies between layers.

And seeing how important on-chip BRAM is directly shaped my updated project idea on the last slide.


--------------------------------------------------------------------------------
[SLIDE 4] Team 06 – Project Idea
--------------------------------------------------------------------------------

Originally, because I saw the FIFO bottleneck in Lab 5, I proposed adding DMA transfers for my term project.
However, after getting the instructor feedback that Lab 7 already uses AXI CDMA—and seeing in my Lab 7 synthesis that BRAM is already at 49% while LUTs and DSPs are under 10%—I realized the real bottleneck to tackle now is BRAM usage and how much data we move over DMA.

So I decided to pivot my project to Weight and Activation Compression with Sparse Zero-Skipping.
My thought was, since ReLU turns all negative values into zeros, more than half of the activations we send over DMA and store in BRAM are just zeros.
If I compress those zero-heavy activations and weights using lossless Run-Length or Bitmask encoding before the DMA transfer, I can shrink both the DMA transfer size and the BRAM footprint.

Then on the FPGA, I'll add a small decoder between the BRAM and the MACs, and update the index generator and MAC enable logic so it simply skips the cycles where the value is zero.
I'll test this on Conv2 to see how much BRAM and inference time I can save without losing any accuracy.

That's all I have—thank you, and I'm happy to take any questions!
