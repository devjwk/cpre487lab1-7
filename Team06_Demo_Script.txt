[SLIDE 1] Team 06 – Jongwoo Kim – Lab 6
--------------------------------------------------------------------------------

Hi everyone, I'm Jongwoo from Team 6.
When I started Lab 6 on the x86 lab machine, I first looked at why the naive convolution was taking 144.7 milliseconds.
I noticed that because the weights are stored in output-channel order, having the input channel in the innermost loop forced the CPU to jump by 32 elements in memory on every step.
So I thought, if I move the output channel (m) to the innermost loop, the CPU can read weights one by one in order and reuse each input value in a register 32 times.
As you can see in the top-left plot, doing it that way made weight accesses completely sequential and dropped my latency from 144.7 milliseconds down to 27 milliseconds—a 5.4x speedup without changing the math at all.

Next, when I tested cache tiling from block size 2 to 32, I initially expected smaller tiles to fit better in L1 cache.
However, when I saw Tile 2 jump up to 235.5 milliseconds, I realized that the extra 9-nested-loop overhead and boundary checks were costing more than the cache benefit, whereas Tile 32 matched our 32 output channels and gave the best tiling latency at 27.4 milliseconds.

For multithreading, I thought splitting across output rows using std::thread would be the cleanest approach because each thread writes to separate memory without locks.
My latency peaked at 4 threads with 8.21 milliseconds—a 17.6x speedup. When I saw 8 to 64 threads slow back down, I realized that since threads are spawned and joined per layer, thread creation overhead and core contention were outweighing the parallel speedup.

Seeing how much memory access mattered on the CPU naturally led into how I approached Lab 7 on the next slide.

[SLIDE 2] Team 06 – Jongwoo Kim – Lab 7
--------------------------------------------------------------------------------

Before building the Lab 7 accelerator, I looked back at my Lab 5 MAC results to decide which MAC architecture to use.
When I compared my Staged and Piped MACs, I saw that the 8-bit Piped MAC ran at 131 megahertz and processed 1 MAC every cycle while using almost the exact same LUTs and flip-flops as the Staged MAC.
Because of that, I thought using four parallel 8-bit Piped MACs in the Lab 7 template would give the best throughput per resource.

While implementing the four hardware modules, I tried to keep the hardware as lightweight as possible.
For the Index Generator, instead of using multipliers to calculate 5D addresses, I thought it would be much more efficient to use only adders with precomputed signed jump offsets.
Then I implemented the four Piped MACs with bias preload, the Dequantization pipeline, and the Output Storage module that does 2-by-2 MaxPooling on the fly using a Read-Modify-Write state machine.

To verify the hardware, I thought debugging all four modules at once on the board would be too painful, so I tested them stage by stage in the Vivado testbench first.
As shown in the top-right waveform, all four stages pass 100% with every fail signal at zero, and full synthesis on the bottom right completed with 9% LUTs, 4% flip-flops, 2% DSPs, and 49% BRAM.
Right now, I am finishing the C++ CDMA integration using MLP.h to run on the ZedBoard—and after hearing Tuesday's presentations, I'll make sure use_lfn is enabled in Vitis first.

Working through these modules led directly to my main challenges and takeaways on the next slide.

[SLIDE 3] Team 06 – Challenges & Takeaways
--------------------------------------------------------------------------------

Looking back at my challenges, both Lab 6 and Lab 7 changed how I think about performance bottlenecks.
In Lab 6, seeing small tiles and high thread counts run slower made me realize that software overhead can easily cancel out theoretical gains.

In Lab 7, the two hardest parts were getting the 5-loop signed address jumps right in index_gen, and getting the BRAM Read-Modify-Write timing right for MaxPooling in output_storage.
Specifically, when I looked at the final write cycle in simulation, I realized that if conv_complete asserts on the same cycle as the last BRAM write enable, the accelerator goes idle one cycle too early. So I thought delaying conv_complete by one clock cycle would let the final pooled byte latch cleanly into BRAM, and that fixed the testbench completely.

Putting Labs 5, 6, and 7 together, my biggest takeaway is that data movement dominates compute performance.
In Lab 5, I saw per-packet FIFO transfers bottleneck a fast MAC; in Lab 6, I saw sequential cache access alone give a 5.4x speedup; and in Lab 7, I saw how double-buffered on-chip BRAM avoids slow DDR copies between layers.

And that realization about on-chip BRAM is what shaped my updated term project on the final slide.


--------------------------------------------------------------------------------
[SLIDE 4] Team 06 – Project Idea
--------------------------------------------------------------------------------

Originally, because I saw the AXI-FIFO transfer bottleneck in Lab 5, I proposed adding DMA transfers for my term project.
However, after reading the instructor feedback that Lab 7 already uses AXI CDMA—and after seeing in my Lab 7 synthesis that on-chip BRAM is at 49% while LUTs and DSPs are under 10%—I thought the real bottleneck we need to solve now is BRAM capacity and DMA data volume.

So I decided to pivot my project to Weight and Activation Compression with Sparse Zero-Skipping.
My thinking is that since ReLU turns all negative activations into zeros, more than half of the activation data we move over DMA and store in BRAM is just zeros.
If I compress those zero-heavy activations and weights using lossless Run-Length or Bitmask encoding before the DMA transfer, I can cut down both the DMA transfer size and the on-chip BRAM footprint.

Then, in hardware, I plan to add a lightweight decoder between the BRAM and the MAC units, and modify the index generator and MAC enable logic so the accelerator skips zero-value MAC cycles altogether.
I'll test this on Conv2 to see how much BRAM and inference latency I can save without losing any accuracy.

Thank you, and I'm happy to take any questions!
